# AD研究所：スリープ復帰後の進捗保持の調査

調査日: 2026-11-10。対象コミット: `5ca49ba4a3de929afdca0b0c8c5f8ed8c9f92bbd`。成果物は本報告と再現テスト。製品コード、設定、変更履歴は変更していない。

## 結論

同じ画面に復帰する模擬試験では、スリープ前の購入・銀河・自動購入設定は保持された。ただし、タイマーを止めて実時計だけを1時間進めても、復帰後のゲーム時計は100msしか進まなかった。再起動では別の経路を通り、12時間の離席に対して8時間分を計算する。これは離席中の時間が反映されない条件であり、保存済みの操作が巻き戻ることとは分けて扱う。

もう一つ、同期済みの保存より古い内容をサーバーから返すと、端末側が前回の同期後に変化していない場合、その内容を自動採用することを再現した。Infinity 2回・購入1回・銀河3・自動購入解放済みから、すべて初期状態へ戻り、端末内の保存も置き換わった。置換前の内容は復旧記録に残る。この試験ではサーバーの内容を意図的に古くし、revisionは増やしている。通常の単一AdStoreが自然に古い内容を返すことを示す試験ではない。

本番の原因と復旧可否は未特定である。端末、OS、ブラウザまたはアプリのバージョン、スリープ時間、操作順、実際の保存データ、添付内容は確認していない。本番で古い応答が返った証拠もない。2件の保持期待は失敗するテストとして残した。期待値を現在の挙動へ合わせる変更、テストのスキップ、製品修正はしていない。

### 採用条件の分岐表

baselineは接続先ID、前回確認したサーバー保存`save`、revision、端末側の比較基準`local`を保持する。比較する基準は`local ?? save`。revisionは書き込み競合と選択の再利用に使うが、通常GETの採用に「前回より新しいrevisionであること」という条件はない。

| 条件（上から優先） | 採用・状態 | 保持上の意味 |
| --- | --- | --- |
| 古い世代・停止前・別プロファイルの応答 | 不採用 | 現在のゲームやrevisionを置き換えない |
| 接続先を採用する意図`adoptRemote`あり | 接続先全体を採用。空ならerror | 大小比較より接続先の選択を優先する |
| リモートなし、または保存全体が一致 | ローカル継続 | 初回はオフライン計算を伴うことがある |
| importPendingあり、前回選択のrevisionと保存全体が一致しない | choice | 両方の元データを保存し、自動上書きを止める |
| importPendingあり、選択が引き続き有効 | ローカル継続 | 選択済みの保存の送信を待つ |
| 同じ接続先のbaselineあり、ローカル不変・リモート変化 | リモート全体を採用 | 変化が古い内容への置換でも採用する。今回の巻き戻り再現条件 |
| baselineあり、双方変化、全体は異なる | choice | 大小比較で一方を捨てず、両方を残す |
| baselineあり、リモート不変 | ローカル継続 | 未同期の購入・銀河・設定を保持し、次にPOSTする |
| baselineなし、全体は異なり比較指標が同じ | choice | 指標に入らない購入等の差も選択の対象になる |
| baselineなし、比較指標が異なる | 指標が大きい側の全体を採用 | 購入等を部分的に合成しない。負けた側にも独自操作がある可能性は残る |
| POSTに対し409 | GETして上記をやり直す | 直ちにどちらかを上書きする処理ではない |

時計だけの更新は`acknowledgeClock`（slice.ts:178）で端末側基準へ反映され、産出も操作もなければ双方更新扱いを避ける。時計だけ進んだ状態をサーバーへ毎回送るわけではない。

## 表示と置換の時系列

同期失敗表示は[adapter.tsx:123](../../client/src/world/antimatter/adapter.tsx#L123)で`adSync === 'error'`から作る。表示処理はゲームを置換しない。

| 場面 | 表示を起こす遷移 | 実際の保存・採用の順序 |
| --- | --- | --- |
| GETまたはPOST中に通信が途切れる | ready/loading→error | catchで端末保存。通常の操作は保持。表示が出ただけではリモート採用はない |
| 通信復旧後の自動再試行 | error→loading→readyまたはchoice | GETを待って採用条件を評価。choiceは更新と保存を止める。採用する場合は復旧記録→端末保存→baseline→画面置換 |
| サーバー保存完了後、応答だけ消失 | ready→error→再試行 | サーバーだけrevisionが進む。同じ内容ならreadyに戻る。応答待ちの間に追加操作があれば、双方更新としてchoiceになり、両方を保持する |
| 古い内容のGETに正常応答 | readyのまま | ローカル不変なら復旧記録を残して古い内容を採用。エラー表示を経ずに巻き戻り得る |
| 端末の定期保存だけ失敗 | 同期表示は変わらない | falseを返すだけ。直後に終了すると未保存の操作を失う可能性。今回、実ブラウザ終了は未検証 |

したがって「エラー表示の後に戻った」という順序だけでは原因を決められない。失敗時刻、再接続GETの内容、採用、次の保存を別々に観測する必要がある。

| プロファイル選択・接続先の採用・選択書き込み中断（同:798、843、886、956） | 複数候補では確認前に通信せず、接続・選択の途中失敗は再開できる。成功 |
| 復旧と再起動前のGET（同:935、984） | 旧応答は現在のゲームとrevisionを変えない。成功 |
| 403と5秒GETタイムアウト（同:296、1003） | 403は同じ権限で自動反復せず、タイムアウトは再接続する。成功 |

既存試験は各目的に必要な項目を比較しており、すべての段階で全コピーを比較する形には作り直していない。追加の統合試験では全コピー比較を置いたが、保存先単体・サーバー単体の試験は対象が異なる。任意のコールバック順序の網羅、GET本文読み込み中だけの切断、POST中の停止と再起動のすべての組み合わせ、復旧一覧・最新キーだけの書き込み失敗、プロファイル選択と同時のOS停止は未検証。実ブラウザでの容量不足、ストレージ消去、タブ強制終了も未検証である。

サーバー試験はOSの一時ディレクトリに隔離した保存先を作り、別のAdStoreを生成して実ファイルを読んだ。`paired`のサーバーはメモリ内の模擬保存であり、ファイル永続化を証明しない。Sは実HTTP応答消失や電源断を発生させた試験ではなく、保存後に応答値を利用しない条件と再読込を検証する。rename失敗後の本体の保持は確認したが、実際のディスク故障・電源断・複数プロセスの同時書き込みの保証ではない。

## 対応案（別途承認後に実装）

推奨は、既存の比較・復旧機構を使って古い候補の自動採用を止める案と、復帰時の時間計算を別々の変更として検討すること。今回の試験だけで本番の原因を決めず、先に必要な証拠を得る。

1. **推奨：疑わしいリモート採用を既存のchoiceへ回す。** 同じ接続先のbaselineと照らし、revisionの後退や、進捗指標が下がる変化は両方の元データを保持して選択待ちにする。指標が同じ場合も購入・銀河・設定を含む全体比較を維持する。意図したリセット・接続先の採用・復旧操作を妨げない例外条件は製品判断が必要。影響は`resolveServer`、選択・復旧画面、全言語の説明、競合テスト。既存のセーブを勝手に部分合成しない。
2. **同じ画面への復帰にも既存のofflineProgressを利用する。** 実時計との差を判定し、復帰時に一度だけ、既存の8時間上限と自動購入の順序で計算する。先にどの保存を採用するか決め、loading・choice中の計算を避ける。二重加算、時計の変更、正常な画面遅延との区別が必要。影響はタイマー・ゲーム時計・オフライン結果表示と同期基準。どこから離席扱いにするかは承認時に決める。ケース52の期待を満たすにはこの経路が必要だが、本番の操作巻き戻りを単独で解決する保証はない。
3. **保存失敗と復帰時の状態を既存UIで確かめられるようにする。** 端末保存の成功・永続保存が使えるか・同期と選択待ちを区別し、既存のエクスポートや復旧一覧へ案内する。既定の保存先やスキーマを増やさず、復旧元を消さない。影響は保存状態、adapter、三言語の文言。自動診断を保存・送信する場合は、対象・同意・保存範囲を先に決める。認証情報や保存全文をログへ出す案は含めない。

範囲外は製品修正、本番設定・認証・接続先の変更、データ移行、復旧元削除、新しい依存パッケージ、公開・リリース。実装前に目的、選ぶ案、既存操作への影響、未確認事項の扱いを提示して承認を得る。

## 実端末で次に集める証拠

聞き取りで得られなかった事項は未確認のまま残す。コードや合成試験では端末固有の条件を確定できない。次の本番検証は利用者の実端末での観測が必要で、今回は未実行。

- 端末・OS、ブラウザまたはアプリとバージョン、スリープの長さを記録する。同じタブの復帰と、閉じて再起動する条件を別にする。
- スリープ前、復帰直後、最初の操作後、エラー表示時、再接続後、次の保存後の順に、購入数・銀河・自動購入設定・Infinity・累計・lastTickと実時刻を比較する。エラーと置換の前後関係を時刻で残す。
- メモリ、端末保存、baselineのrevision、GETのrevisionと保存の要約、実際に採用された状態を照合する。調査用の要約には接続トークン・鍵・環境変数・会話内容を含めない。復旧記録は接続情報を含むため、そのまま公開しない。
