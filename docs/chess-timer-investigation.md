# 配置したチェスがタイマー操作用に見える件の調査

通常配置のチェスが放置中にタイマー操作用へ変化した原因は、今回も特定できていない。タイマーを開始するチェスのデモ配置は存在するが、報告された個体と同一かは未確認である。添付画像は未確認で、対象セッションの状態も取得できていない。外見や位置だけでデモと判断しない。

調査対象は開始時点のコミット `f70a515f57b5f9ef02e998d16f969f5647f3bd19`。変更はこの報告と既存テストへの検証追加に限定した。デモ、製品コード、変更履歴は変更していない。

指定のテスト4種と完了チェックはすべて起動を試みたが、Node/npm の管理ツールである Volta がアクセス拒否で終了し、テスト本体には到達しなかった。以下のコードからの判断と、未実行の検証手順を区別する。再現試験に合格した、あるいは不具合がないという結論ではない。

## まず対象をIDで照合する

根拠は `shared/system-demo.ts` の `systemDemoMap`、`shared/system-items.ts` の `systemItemInstanceId`、`server/index.ts` の `handleSession`（`itemCreate`）。照合する値は次のとおり。

| 項目 | デモの定義 | 報告対象 |
| --- | --- | --- |
| 実体のアイテムID | `system-map:system-demo:menu-chess-button` | 未取得 |
| `kind` | `chess` | 未取得 |
| `mapPlacement.mapId` | `system-demo` | 未取得 |
| `mapPlacement.objectId` | `menu-chess-button` | 未取得 |
| `mapPlacement.itemId` | `chess` | 未取得 |
| `mapPlacement.mode` | `system` | 未取得 |
| 定義上の位置 | `[1.5, 0, 0]` | 未取得 |
| セッション内の共有システムのマップID | デモが有効なら `system-demo` | 未取得 |

このデモは `menu-start` のボタン操作を `countdown` の `start` に接続している。初めからタイマー操作用であり、通常チェスから変わる処理ではない。通常配置はサーバーがUUIDを生成し、`mapPlacement` を付けずに作る。配置時に空きを探して位置をずらす場合もあるため、位置の一致・不一致は補助情報にとどめる。

同一性を確定するには、対象セッションと対象アイテムの上記項目を照合する必要がある。セッションの共有マップIDだけでも不十分で、同じセッションに通常配置のチェスが共存できる。

## 通常配置を書き換える経路は確認できていない

### 生成から定期処理まで

`shared/items.ts` の `createItem` はチェスの初期盤面を作る。`applyItemAction` のチェス分岐が変えるのは盤面、着手、更新者などで、`mapPlacement.mode` を時間に応じて追加する処理はない。

`server/index.ts` の `syncSystemItems` は `server/system-items.ts` の `reconcileSystemItems` を呼ぶ。この関数はマップIDとオブジェクトIDから実体IDを作り、そのIDのアイテムだけを再調整する。位置や `kind` が同じという理由で通常アイテムを取り込む処理はない。削除対象も不要になった `mapPlacement` 付きのアイテムに限る。

呼び出しを次の範囲で確認した。

| 呼び出し元（`server/index.ts`） | 起きること |
| --- | --- |
| `sendSessionSnapshot` | アイテムと共有状態を配る前に再調整。まだ同期済みの印がなければ、不足するnative配置の生成を許可する |
| `handleSession` の `systemResync` | 再調整して共有状態を返す |
| `systemLoad` / `systemCommand` | 共有状態を更新後に再調整。明示したマップ再読込では不足するnative配置も作る |
| `itemRemove` の旧タイマーカメラ削除経路 | マップの更新後に再調整。通常チェスの生成経路とは別 |
| `leave` | 退出処理後に再調整。最後の参加者の退出では共有システムをメモリから解放する |
| `systemTick`（100ミリ秒間隔） | 参加者がいるセッションの共有状態を進め、native配置の再生成をせず再調整 |

`SystemService.tick` は登録済みシステムの更新確認（`refresh`）と予約処理（`tick`）を行う。`SystemRuntime.refresh` は共有システムの版を更新するが、マップ内の `itemMode` を時間で変更しない。`SystemRuntime.tick` は期限に達した予約処理を実行する。参加者がいないセッションをこの定期処理で進める構造ではないため、在室したままの放置と全員退出後の再入室は別条件として扱う。

### マップ配置では定義の変更によって操作用途が変わり得る

`reconcileSystemItems` の競合確認は、実体IDに対する `mapId` / `objectId` の不一致、または配置識別情報の欠落を拒否する。`itemId` / `mode` まで違えば必ず競合になる、という意味ではない。

同じマップID・オブジェクトIDのまま定義上の `itemMode` をnativeからsystemへ変更すると、同関数の `sameAsset` が偽になり、マップ配置を作り直す経路がある。これは定義変更時の挙動で、通常配置のUUIDを変化させる証拠ではない。今回のデモは変更していない。報告時にマップの定義や版が変わったかは未確認である。

## アイテムと共有状態の保存時点は一致するとは限らない

`server/index.ts` の `saveItems` は変更のあったセッションを5秒ごとに保存待ちの列へ渡す。`server/db/persist.ts` の `enqueue` / `drain` は書き込みを順序付け、終了時に待つ。`server/db/content-store.ts` の `saveItems` はセッションとアイテムIDをキーに、アイテム全体をDB内のトランザクションで保存する。`loadContent` は起動時にその保存値を読み出す。

復元側の `registerSession` は既知の種類を読み込み、`settle` で持ち主や編集中などの一時状態を外す。チェスの盤面、ID、配置識別情報を別用途へ変換する処理はこの範囲では見つからなかった。

一方、`server/system-service.ts` の `SystemService.runtime` はセッションごとの共有状態を別ファイルから復元する。`SystemRuntime.commit` は `atomicJSON` による保存に成功した後でメモリ上の状態を更新する。アイテムDBと共有状態ファイルを一緒に確定する処理はない。このため再起動時、共有状態に比べてアイテム側の保存が古い組み合わせは起こり得る。

復元後は `syncSystemItems` が現在の共有マップと照合する。system配置は共有状態へ追従し、定義が同じnative配置は既存の盤面を保持する。通常配置はその対象にならない。ただし、これはコード上の境界の確認であり、DB保存直後のサーバープロセス再起動や保存途中の強制停止を再現した結果ではない。保存失敗、マップ定義変更、古い保存値の混在による表示の影響は残る。

## パネルの選択と実際の操作先は別に確認する

`client/src/net/ws.ts` の `applySessionSnapshot` は現在のセッションIDを確認し、そのセッションのアイテム一覧をIDで置き換える。`onMessage` の `item` はセッションID・アイテムIDでアイテム全体を更新し、`itemMove` は座標、`itemRemove` は指定IDを削除する。受信処理が位置をもとに二つのチェスを統合する処理は見つからなかった。チェスの着手はサーバーからアイテム全体が返る経路である。

`client/src/net/session.ts` の `configureSessionSync` は接続の世代、送信元、接続ごとの認可情報、受信順序を確認し、古い接続の受信処理を除外する。`client/src/systems/state.ts` の `receiveSystems` は同一セッションで古いrevisionの差分を拒否し、スナップショットは受け入れる。表示側のアイテム一覧は `client/src/sessionView.ts` の `deriveSession` で現在のセッション分から切り出す。

| 表示・操作箇所 | 判定 |
| --- | --- |
| `world/NearList.tsx` の `ActionMenu` | 現在の一覧からメニューのアイテムIDで引き、`mode === 'system'` なら共有システム用パネル |
| `world/WindowLayer.tsx` の `useResolved` | ウィンドウのキーからアイテムIDを引き、同じmode判定でパネルを選ぶ。実体がなければ表示しない |
| `view3d/items3d.tsx` の `Item3D` / `NativeItem3D` | `kind` に沿ったモデルを描き、system配置なら操作を `SystemItemBoundary` で包む |
| `systems/map-item-control.ts` の `controlledItemObject` | modeに加え、現在のセッション、共有状態のセッション、マップID、実体ID、objectId、itemId、定義のitemModeを照合 |
| `systems/SystemItem.tsx` の `useSystemItem` | 描画時に操作可否を確認し、クリック時にも最新のアイテムを取得して操作先を照合 |

パネルが「共有システム用」になること自体はmodeだけで決まる。共有状態が未着・不整合なら、パネルは出ても実行ボタンは出ない場合がある。したがってパネルの説明だけを見て「タイマーへ接続された」とは判定できない。`kind === 'chess'` の外見が残ったままタイマーを操作するデモも、この表示経路に合致する。

ウィンドウやメニューは現在の一覧をIDで参照し、`client/src/actions.ts` の `joinSession` / `leaveSession` が呼ぶ入退室処理はウィンドウ一覧を空にする。保存した古いアイテムオブジェクトだけを使い続ける構造は、この範囲では見つからなかった。ただし、ブラウザでの表示順序、再接続中の一時的な表示、開いたままの2Dメニュー・ウィンドウと3Dの実操作は未検証である。受信したアイテム自体に古い・誤ったmodeが入っていた場合まで否定するものではない。

## 仮説ごとの判断と、次に必要な証拠

| 仮説 | 確認範囲・否定できた範囲 | 残る可能性と次の確認 |
| --- | --- | --- |
| 初めからあるデモを通常チェスと取り違えた | デモの実体IDと接続先をコードで確認。報告対象との同一性は未確認 | 対象ID・配置情報・共有マップIDを照合する。画像・位置だけでは確定しない |
| 時間経過で通常チェスをデモへ取り込んだ | 現行コードで、同位置・同種類を理由に通常UUIDを取り込む経路は見つからない。定期再調整はマップ由来IDを使う | 実際に使われた版と変更前後の同じIDの値が必要。未実行のテストで再現しないとすらまだ言えない |
| マップ配置の定義が変わった | 同じmapId/objectIdでmode変更時に再作成する経路を確認。単なる放置による変更とは区別した | 対象がnativeのマップ配置か、発生時にマップ再読込・定義更新があったかを確認する |
| 保存と復元の時点がずれた | 二つの保存先が別に確定することを確認。通常盤の取り込みは見つからないが、古い状態の混在は否定できない | 保存完了後の実プロセス再起動、保存途中の停止、保存失敗、マップ再読込を隔離環境で比較する |
| 古い接続やウィンドウ参照で誤表示した | セッション・IDでの参照、接続世代・受信順序、クリック時の再照合を確認。modeだけのパネル選択と操作解決を区別した | 二クライアントで同じIDを確認し、2Dメニュー・開いたウィンドウ・3Dの操作表示を比較。表示だけか実際にタイマーが動くかも分ける |

次の証拠は、対象セッションを特定できる情報、発生日時とおよその放置時間、操作表示の画像または正確な文言、可能なら対象アイテムIDに限定する。認証情報や保存データ全体は不要である。

まず実行環境を整えて追加テストを実行し、保存完了後のサーバー再起動を含む隔離試験を行う。そのうえで対象セッションと同じ実時間の放置条件を再現する。原因が確定した場合に変更対象を提案し、修正実装は別の作業として扱う。今回の調査だけを根拠に、デモの置換や製品挙動の変更は行わない。
